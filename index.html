    How it worked

    The six SOAR workflows

    Each one follows the same shape: trigger, enrichment, decision, action. Analysts start from a prepared incident instead of a raw alert, which is where the 30% cut in investigation time came from.

    • Security alert triageWhen an alert arrives from Microsoft Defender, the SIEM, or the email security toolCreates the security incident, extracts indicators of compromise, assigns severity, routes it to the right team, and generates investigation tasks.
    • User enrichmentWhen a user account is involved in an alertQueries Active Directory for the user’s department, manager, and privilege level, so the analyst has context immediately.
    • Malware responseWhen an endpoint reports a malware detectionCreates the incident, sets severity, notifies the security team, and launches the investigation checklist.
    • Phishing investigationWhen a user reports a suspicious emailCreates the ticket, extracts the sender and domain, gathers the email metadata, and routes it to the security queue.
    • Privileged access reviewWhen access is requested or a privileged account comes up for reviewValidates approvals, routes to the right approvers, and keeps an audit trail.
    • Incident escalationWhen an alert is rated criticalNotifies stakeholders, creates tasks, escalates to the incident commander, and tracks the SLA.

    Access provisioning with least privilege

    1. The request comes in and the flow checks whether the person is a new hire or a returning employee.
    2. For a new hire, IntegrationHub creates the Active Directory account and assigns group memberships based on the role.
    3. The same flow opens the workstation request, ID card provisioning, workspace allocation, and role-based software installs.
    4. Nothing is granted until the manager approves, which prevents over-provisioning and privilege creep.
    5. MFA is enforced at the identity level through Microsoft Entra ID.

    Offboarding runs in reverse: the Active Directory account is deactivated as soon as HR opens the case, so no orphaned accounts are left behind.

    AI in the incident process

    • Virtual Agent creates tickets and handles common requests.
    • Now Assist summarizes incidents so agents read less raw ticket data.
    • Predictive Intelligence categorizes and assigns tickets based on historical data.

    Audit and response

    Every identity action, from account creation and group changes to access grants and deprovisioning, is logged in Entra ID and the ServiceNow workflow audit trail. If an unauthorized privilege assignment appears, the response is to review the audit logs, pull an access report, revoke the role immediately, disable the faulty workflow, fix its logic, and add alerting for high-risk access events.

AWS IAM security assessment and remediation

The setup

Cloud IAM misconfigurations are among the most common causes of cloud breaches. I built an AWS environment with six of them on purpose, attacked it, built detection for it, fixed it, and proved the fixes with a before-and-after scan.

Create the weakness → Exploit → Detect and monitor → Remediate → Validate

What was broken

MisconfigurationSeverity
Over-permissive IAM policy (*:*)Critical
Privilege escalation through AssumeRoleCritical
Public S3 bucketHigh
Sensitive credentials stored in that bucketHigh
No CloudTrail loggingHigh
MFA disabled for an IAM userMedium

How it was exploited

A low-privilege user’s policy let it assume any role, including an admin role. One call produced temporary administrator credentials:

aws sts assume-role \
  --role-arn arn:aws:iam::<ACCOUNT_ID>:role/vulnerable-admin-role \
  --role-session-name privilege-escalation-test

Low-privilege user → AssumeRole → temporary admin credentials → full environment control

Separately, the public bucket served a credentials file to anyone with the URL, no authentication required.

Detection I built

  • Multi-region CloudTrail with log file validation, capturing IAM changes, console logins, API calls, and role assumptions.
  • CloudWatch metric filters and alarms: Root-Account-Login-Alert and Console-Login-Without-MFA-Alert.
  • SNS email alerts on every triggered alarm, the same shape as a SOC alerting pipeline.

What I changed

  • Removed AdministratorAccess from the user and deleted the AssumeAnyRolePolicy; permissions scoped to required actions only.
  • Removed the public bucket policy, re-enabled Block Public Access, restricted object-level access.
  • Enabled MFA for the IAM user.

How I proved it

MFADisabledEnabled
CloudTrail, CloudWatch, SNSNot configuredRunning

*The one remaining check concerns AWS Firewall Manager, outside the scope of this IAM-focused lab.

Limitations and next steps

This is one lab account with planted issues, and Prowler’s 216 failures cover the whole account, not only those six. Next, I’d codify the fixes in Terraform and add AWS Config rules so configuration drift is caught automatically.

Case file 2 of 3

DevSecOps automated security gate

The setup

A Flask API in Docker, built with seven OWASP API Top 10 weaknesses, then taken through the full secure development loop: scan, exploit, fix, re-scan, and automate the scans so the same mistakes can’t ship again.

Vulnerable API → SAST + SCA + secret scan + container scan + DAST → Remediation → Validation

What was broken

VulnerabilityOWASP APISeverityFix
Broken object-level authorizationAPI1CriticalOwnership check on every request
Broken authenticationAPI2CriticalHardened JWT, managed secret
Sensitive data exposureAPI3HighOutput filtering, data minimization
No rate limitingAPI4HighFlask-Limiter
Broken function-level authorizationAPI5CriticalRole-based middleware
Security misconfigurationAPI8HighNginx hardening, security headers
Hard-coded secretsAPI8HighMoved to environment variables

How it was exploited

Any user could read any other user’s record by changing the ID in the URL, and the admin endpoint answered anyone:

curl http://127.0.0.1:8000/users/2    # another user's data
curl http://127.0.0.1:8000/admin      # admin functions, no role check

With the JWT signing secret sitting in source code, anyone with repository access could forge a valid token and take over any account.

What I changed

  • JWT authentication plus authorization middleware; RBAC for admin routes; every object request checked against the requesting user. The BOLA request now returns 403 Forbidden.
  • Secrets moved out of code into environment variables; GitLeaks confirmed none remain in the repository history.
  • Passwords hashed with werkzeug.security instead of stored in plaintext.
  • Nginx reverse proxy hides the framework and sets Content-Security-Policy, X-Content-Type-Options, X-Frame-Options, and Referrer-Policy.
  • Flask, PyJWT, and Werkzeug upgraded to patched versions.
# before
JWT_SECRET = "supersecretkey123"
# after
JWT_SECRET = os.getenv("JWT_SECRET")

The pipeline

Every push runs Bandit, pip-audit, GitLeaks, a Docker build, and Trivy in GitHub Actions. If a security gate fails, the build is blocked. OWASP ZAP tests the running app for what static scans can’t see.

Limitations and next steps

The vulnerabilities were planted in a small API, and container results change as new CVEs are published, so a scan today finds more than the 8 recorded at the time. Next, I’d fail builds only on fixable high and critical issues (--ignore-unfixed) and move to a minimal base image.

Case file 3 of 3

AI threat simulation and RAG hardening

The setup

An internal company assistant built with Streamlit, LangChain, OpenAI, and ChromaDB, answering questions from four documents of different sensitivity: an employee handbook (internal), a security policy and an incident response plan (confidential), and a finance report (highly confidential). Then I attacked it.

User → Streamlit → security controls layer → LangChain → ChromaDB retriever → documents → OpenAI → validated response

How it was exploited

Before hardening, a plain question was enough to pull confidential figures, and the app listed the confidential finance report as its source.

Attack scenarioBeforeAfter
System prompt extractionSucceededBlocked
Instruction override (“developer mode”)SucceededBlocked
Context window extractionSucceededBlocked
Employee data extractionSucceededBlocked
Financial data extractionSucceededBlocked
Executive data extractionBlockedBlocked

What I changed

  • Input filtering: detects and blocks prompt injection and instruction-override patterns.
  • Output validation: checks every response for sensitive patterns such as personal data and financial figures before it reaches the user.
  • Access control: document-level retrieval restrictions, no raw retrieved context in answers, and responses limited to approved question types.

Normal questions still work. Asked for the password policy, it still answers: at least 12 characters with uppercase, lowercase, numbers, and special characters.

How I proved it

MeasureBeforeAfter

Limitations and next steps

The input filter is pattern-based, so a determined attacker could rephrase around it, and six scenarios is a small test set. Next, I’d build a larger adversarial test suite that runs automatically on every change.
